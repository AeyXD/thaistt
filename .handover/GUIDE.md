# แนวทางเขียน HANDOVER

ใช้กับ `.handover/HANDOVER.md` ของ repo นี้ (และ repo อื่นใน ecosystem ได้) —
สรุปจากปัญหาที่เจอจริงตอนตรวจ thaistt 2026-11-02

## หลักการ

1. **ผู้อ่านคือ agent ตัวถัดไปที่ไม่มี context** — อ่านจบต้องตอบได้ 4 ข้อ:
   ตอนนี้อยู่ไหน · อะไรใช้ได้จริง · ทำอะไรต่อ · มีกับดักอะไร
2. **เป็น "สถานะ" ไม่ใช่ "บันทึกประจำวัน"** — ข้อความที่ไม่จริงแล้วให้แก้หรือลบ
   ห้ามเขียนต่อท้ายให้ขัดกันเอง · ประวัติให้ git log / ตารางเวอร์ชันเก็บ
   - เคสจริง: "resume ได้ — พังตรงไหนรันซ้ำต่อจากนั้น" ไม่จริงตั้งแต่ v0.2 แต่อยู่ในเอกสารถึง v0.6.1
3. **backlog มีที่เดียว** — คำขอ/บั๊กจาก session อื่นต้องย้ายเข้ารายการงานพร้อมสถานะทันที
   - เคสจริง: บั๊ก manifest ถูกเขียนทับ อยู่แค่ในหัวข้อ "บั๊กจากการใช้จริง"
     ไม่อยู่ใน "ที่ยังจองเหลือ" → ตกหล่นข้ามเวอร์ชัน
4. **ทุกข้ออ้างตรวจย้อนได้** — commit hash · วันที่ · จำนวนเทส · สถานะ CI ·
   และบอกระดับความมั่นใจ:
   - ✅ พิสูจน์กับของจริง (สื่อจริง / binary จริง)
   - 🧪 พิสูจน์ด้วยเทส / fake binaries
   - 📖 จากการอ่านโค้ด ยังไม่ได้รัน
5. **สิ่งที่กระทบผู้ใช้ปลายทางขึ้นบนสุด** — พฤติกรรมที่เปลี่ยน, ข้อจำกัดที่ยังไม่แก้
   (เช่น manifest ไม่ออก `skip` สำหรับคลิป resume แล้ว — สคริปต์ W1/W2 ต้องรู้)
6. **เรียงจากสำคัญ → น้อย และคุมความยาว** — ส่วน §1–§3 ควรจบใน ~60 บรรทัด ·
   รายละเอียดยาวย้ายไปท้ายไฟล์หรือไฟล์แยก
7. **จดทางตาย / การตัดสินใจไว้ถาวร** — ในหัวข้อของมันเอง ไม่ฝังในประวัติเวอร์ชัน
   (เช่น `--print-confidence` ใช้ไม่ได้, whisper.cpp ธง output สองสไตล์)

## โครงไฟล์

```markdown
# HANDOVER — <repo>
อัปเดต: YYYY-MM-DD · โดย: <session> · HEAD `<hash>` · เทส N (skip M) · CI ✅/❌

## 1. สถานะตอนนี้ (≤10 บรรทัด)
- เวอร์ชัน · ใช้ได้แค่ไหน · ใครใช้อยู่
- ⚠️ ที่ผู้ใช้ต้องรู้: พฤติกรรมที่เปลี่ยน / ข้อจำกัดที่ยังไม่แก้

## 2. ทำต่ออะไร (backlog เดียว — เรียงตามความสำคัญ)
| # | งาน | ที่มา | สถานะ | หมายเหตุ / เงื่อนไข |
|---|---|---|---|---|
| 1 | ... | W1 ข้อ 2 · W2 ข้อ 8 | รอหลักฐาน / พร้อมทำ / กำลังทำ | ... |

## 3. กับดัก / การตัดสินใจ / ทางตาย
- <สิ่งที่ห้ามเลิกทำ หรือห้ามลองซ้ำ> → <เหตุผล + หลักฐาน>

## 4. วิธีตรวจว่ายังดีอยู่
- คำสั่งเทส · fixture จริง (env ที่ต้องตั้ง) · สิ่งที่ต้องลองด้วยมือ

## 5. Inbox จาก session อื่น
- ดิบ ลงวันที่ + ผู้ส่ง · ย้ายเข้า §2 แล้วขีดฆ่า (~~...~~ → §2 #n)

## 6. ประวัติเวอร์ชัน
| เวอร์ชัน | สาระ | commit |
|---|---|---|
| vX.Y | 1 บรรทัด | `hash` |
```

## บันทึกการแก้บั๊ก (ใช้ใน §6 หรือหัวข้อบันทึกการตรวจ)

ต่อบั๊กหนึ่งตัว เขียน 4 บรรทัด:

- **เจออะไร** — อาการที่ผู้ใช้เห็น + ใครเจอ/รายงาน
- **ผิดยังไง** — สาเหตุในโค้ด (ฟังก์ชัน/จุด) และผลกระทบจริง
- **แก้ยังไง** — แนวทาง + commit hash + พฤติกรรมที่เปลี่ยน
- **พิสูจน์ยังไง** — เทสที่เพิ่ม (แดงก่อนแก้ เขียวหลังแก้) / ทดสอบกับของจริง
